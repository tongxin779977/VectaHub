# 评分维度详细说明

本文档详细说明 20 个评分维度的评分标准、扣分规则和检查方法。

---

## 第一组：架构设计（Architecture）

### D01 - 模块职责单一性

**对应条例**：G-01, G-03

**评分标准**：

| 分数 | 标准 |
|------|------|
| 5 | 每个文件职责单一，无超过 300 行的文件，模块边界清晰 |
| 4 | 存在 1-2 个文件略超 300 行，但职责仍然清晰 |
| 3 | 存在 3-5 个大文件，或有 1 个文件职责不清晰 |
| 2 | 多个文件职责混乱，存在"上帝文件" |
| 1 | 模块边界严重模糊，职责高度耦合 |
| 0 | 无模块化，所有代码混杂在一起 |

**扣分规则**：

| 问题 | 扣分 | 严重程度 |
|------|------|----------|
| 单文件超过 300 行 | -0.5/个 | P2 |
| 单文件超过 500 行 | -1/个 | P1 |
| 单函数超过 50 行 | -0.5/个 | P2 |
| 单函数超过 100 行 | -1/个 | P1 |
| 文件职责不单一（混合了不相关的功能） | -1/个 | P1 |
| 模块边界模糊（职责重叠） | -2 | P1 |

**检查方法**：
1. 统计每个文件的行数
2. 统计每个函数的行数
3. 检查文件是否包含不相关的功能
4. 检查模块间的职责边界

### D02 - 依赖方向合理性

**对应条例**：G-08, 3P-05

**评分标准**：

| 分数 | 标准 |
|------|------|
| 5 | 依赖方向清晰，无循环依赖，使用依赖注入解耦 |
| 4 | 依赖方向基本正确，有 1-2 个可改进的依赖关系 |
| 3 | 存在 1 个循环依赖或反向依赖 |
| 2 | 存在多个循环依赖或反向依赖 |
| 1 | 依赖关系混乱，难以理解模块间关系 |
| 0 | 存在严重的循环依赖，导致无法独立测试 |

**扣分规则**：

| 问题 | 扣分 | 严重程度 |
|------|------|----------|
| 循环依赖 | -2/对 | P0 |
| 反向依赖（上层被下层依赖） | -2/对 | P0 |
| 直接依赖具体实现而非接口 | -0.5/个 | P2 |
| 缺少依赖注入，导致难以测试 | -1 | P1 |

**检查方法**：
1. 分析模块间的 import 关系
2. 检查是否存在循环依赖
3. 检查依赖方向是否符合层次结构
4. 检查是否使用了依赖注入

## 第二组：类型安全（Type Safety）

### D04 - 类型完整性

**对应条例**：TS-07, TS-04

**评分标准**：

| 分数 | 标准 |
|------|------|
| 5 | 无 `any` 类型，所有参数和返回值都有类型标注 |
| 4 | 存在 1-2 个 `any` 使用，但有合理理由 |
| 3 | 存在 3-5 个 `any` 使用 |
| 2 | 多处使用 `any`，或有类型断言绕过检查 |
| 1 | 大量使用 `any`，类型系统形同虚设 |
| 0 | 几乎无类型标注 |

**扣分规则**：

| 问题 | 扣分 | 严重程度 |
|------|------|----------|
| 使用 `any` 类型 | -0.5/个 | P1 |
| 使用 `as any` 类型断言 | -1/个 | P0 |
| 函数参数缺少类型标注 | -0.5/个 | P2 |
| 函数返回值缺少类型标注 | -0.5/个 | P2 |
| 使用 `@ts-ignore` 而非 `@ts-expect-error` | -0.5/个 | P2 |

**检查方法**：
1. 搜索 `any` 关键字
2. 搜索 `as any` 类型断言
3. 检查函数签名是否有类型标注
4. 检查 `@ts-ignore` 和 `@ts-expect-error` 的使用

| 顶层导出缺少 JSDoc | -0.5/个 | P2 |
| 注释描述"做了什么"而非"为什么" | -0.5/个 | P3 |
| 过时注释 | -0.5/个 | P2 |
| 文档与代码不同步 | -1 | P1 |
| 缺少 `@deprecated` 标记 | -0.5/个 | P2 |

**检查方法**：
1. 检查顶层导出是否有 JSDoc
2. 检查注释是否解释了原因
3. 检查是否有过时注释
4. 检查文档是否与代码同步

### D19 - 代码重复度

**对应条例**：G-03, G-08

**评分标准**：

| 分数 | 标准 |
|------|------|
| 5 | 无明显重复代码，DRY 原则执行良好 |
| 4 | 存在 1-2 处轻微重复 |
| 3 | 存在 3-5 处重复代码 |
| 2 | 多处重复代码 |
| 1 | 大量重复代码 |
| 0 | 代码高度重复 |

**扣分规则**：

| 问题 | 扣分 | 严重程度 |
|------|------|----------|
| 可提取为公共函数的重复逻辑 | -0.5/处 | P2 |
| Copy-paste 代码 | -1/处 | P1 |
| 重复的类型定义 | -0.5/处 | P2 |

**检查方法**：
1. 检查是否有重复的代码块
2. 检查是否有可提取的公共函数
3. 检查是否有重复的类型定义

### D20 - 技术债务标记

**对应条例**：G-09

**评分标准**：

| 分数 | 标准 |
|------|------|
| 5 | 技术债务有标记，有追踪，有清理计划 |
| 4 | 基本符合，有 1-2 个可改进点 |
| 3 | 存在 3-5 个未标记的技术债务 |
| 2 | 多个未标记的技术债务 |
| 1 | 技术债务严重 |
| 0 | 技术债务失控 |

**扣分规则**：

| 问题 | 扣分 | 严重程度 |
|------|------|----------|
| 未标记的 TODO/FIXME | -0.5/个 | P3 |
| 已废弃代码未清理 | -0.5/个 | P2 |
| 已知问题未修复 | -1/个 | P1 |
| 技术债务无追踪 | -0.5 | P2 |

**检查方法**：
1. 搜索 TODO, FIXME, HACK 标记
2. 检查是否有 deprecated 代码未清理
3. 检查是否有已知但未修复的问题
4. 检查技术债务是否有追踪
