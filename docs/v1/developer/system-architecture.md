## 1. 系统架构

### 1.1 分层模型

1.  **交互层**: 处理用户输入（自然语言或 YAML），提供命令编辑与预览功能。
2.  **引擎层**: 负责步骤编排、上下文管理、DryRun 预览及执行记录持久化。
3.  **执行层**: 实现安全协议检查、正则检测及多平台沙箱隔离，并记录审计日志。

### 1.2 架构改进 (1.1 更新)

在 1.1 版本中，系统对原有架构进行了以下优化：

1.  **命令行审计**: 将 `CLI + Args` 合并为完整字符串后再通过 `Detector` 扫描，以检测参数中的风险。
2.  **进程管理**: 插件端增加了 `ProcessManager`，在插件停止时关闭关联的子进程。
3.  **日志可靠性**: 增加了进程退出钩子，在程序关闭时尝试将缓冲区中的日志写入磁盘。
4.  **目录隔离**: 通过 `VECTAHUB_HOME` 统一管理应用数据路径，减少对用户主目录的直接依赖。

### 1.3 核心组件

| 组件 | 职责 |
|------|------|
| **NL Parser** | 将自然语言转换为结构化任务列表。 |
| **Workflow Engine** | 管理工作流的加载、排序与执行状态。 |
| **Executor** | 调用安全检测并执行具体的子进程。 |
| **Sandbox** | 提供隔离的命令运行环境。 |
| **LLM Client** | 封装对外部模型 API 的调用。 |
| **Storage** | 负责工作流与执行记录的本地持久化。 |

## 2. 核心数据结构

### 2.1 Workflow (工作流)

```typescript
interface Workflow {
  id: string;
  name: string;
  mode: 'strict' | 'relaxed' | 'consensus';
  steps: Step[];
}
```

### 2.2 Step (步骤)

```typescript
interface Step {
  id: string;
  type: 'exec' | 'for_each' | 'if' | 'parallel' | 'opencli';
  cli?: string;
  args?: string[];
  body?: Step[];
}
```

## 3. 自然语言处理

系统采用分句、匹配、协调的流程：
1.  **分句**: 将输入拆分为独立意图。
2.  **匹配**: 基于关键词权重、短语正则和 CLI 模式计算置信度分数。
3.  **协调**: 解决多意图冲突并生成最终任务列表。

置信度分级：
-   **High (≥ 0.7)**: 自动处理。
-   **Medium (≥ 0.5)**: 处理并显示提示。
-   **Low (≥ 0.3)**: 建议用户确认。

---

## 4. 安全机制

### 4.1 检测流程

1.  **规则引擎**: 检查黑白名单配置。
2.  **安全协议**: 匹配预定义的安全性规则。
3.  **危险检测**: 使用 `ShellTokenizer` 分解复合命令，并对子命令进行正则扫描。

### 4.2 执行模式

-   **STRICT**: 阻断所有潜在风险命令。
-   **RELAXED**: 允许常规操作，阻断已知高危操作。
-   **CONSENSUS**: 关键操作需人工确认。

## 6. VS Code 插件开发规范

### 6.1 开发原则
- 插件第一优先级是提高日常开发效率，不是堆满高级入口。
- 任务面板只展示高频、必要、当前项目真实存在的任务。
- 任何执行路径必须经过统一 CLI adapter，不得绕过 VectaHub CLI 直接执行自然语言生成的命令。
- 自然语言执行默认 `strict + preview first`。
- 危险命令、高风险修复、批量修复必须有确认或暂停机制。
- 自动化任务必须有状态：pending、running、completed、failed、cancelled 或 needs-confirmation。
- 长驻任务必须可停止，插件退出时必须清理子进程。
- 所有新增能力必须配套测试，不能只改 UI。
- 错误消息必须告诉用户失败点和下一步，不能只显示 unknown error。
- 不要把 CLI 人类日志解析成 UI 状态。
- 不要暴露内部堆栈作为用户第一层错误信息。
- Output Channel 不得输出 API key、完整环境变量或未脱敏 secret。

### 6.2 禁止事项
1. 不要在插件里静默安装 CLI。
2. 不要绕过 VectaHub CLI 直接执行自然语言生成的命令。
3. 不要默认使用 relaxed 模式。
4. 不要做 Webview Chat。
5. 不要做 DAG / 图形化 workflow 编辑器。
6. 不要把 Tools、Security、Workflow 概念默认平铺给新用户。
7. 不要通过 shell 拼接用户输入，必须使用 `spawn` + args 数组。
8. 不要在 Output Channel 输出 API key 或未脱敏 secret。
9. 不要把 CLI 人类日志作为长期 UI 状态解析方案。
10. 不要暴露内部堆栈作为用户第一层错误信息。
11. 不要声称 Windows/Linux 已支持（macOS first）。

### 6.3 交付前检查清单
| # | 检查项 | 说明 |
|---|--------|------|
| 1 | 测试配套 | 每个变更是否有对应测试？ |
| 2 | 验证证据 | 是否已运行测试并保留输出？ |
| 3 | 类型安全 | `npm run typecheck` 是否通过？ |
| 4 | 危险命令防护 | `rm`, `sudo` 等是否有确认对话框？ |
| 5 | NL 预览优先 | 自然语言执行是否先 preview 再 run？ |
| 6 | 敏感数据隔离 | Output 是否包含 API key 或未脱敏 secret？ |
| 7 | 错误可操作性 | 错误消息是否包含失败点和下一步建议？ |

### 6.4 核心成果 (M0-M8)
- **任务智能识别**：自动分类识别 dev, test, lint, typecheck, build, watch, storybook 等 20+ 种任务。
- **一键开发链**：支持一键运行 `typecheck -> lint -> test -> build` 的完整质量检查链。
- **长驻任务管控**：完善的 dev server 启动、状态追踪与进程回收机制。
- **CI 失败闭环**：一键同步 GitHub Actions 错误，自动转化为本地诊断队列任务。
- **批量诊断自动化**：支持一键批量处理诊断队列，具备进度追踪、中途取消与失败摘要功能。
- **安全防线**：内置本地危险模式拦截器（rm, sudo 等）并深度集成 CLI 安全检测协议。
- **工程标准**：全量迁移至 Vitest 测试体系，230 个测试用例确保协议收敛与逻辑可靠。

## 7. 模块封装与执行边界

为保证系统的稳定性和可维护性，VectaHub 遵循严格的通用封装和职责边界原则：

### 7.1 通用协议收敛
- **CLI 与 VS 插件数据统一**：两端共享统一的 `ExecutionPlan` JSON 协议和诊断队列（`DiagnosticQueue`）Schema。VS Code 插件作为消费者，直接读取 CLI 产出的标准数据结构（如执行步骤、用户报告），不再在插件侧重复推导业务计划。
- **上下文探测隔离**：项目的环境探测（如包管理器、Git Remote）集中在纯 Node.js 实现的 `ProjectContext` 模块中，核心执行引擎严禁引入 `vscode` API。

### 7.2 封装纪律
- 只抽取已有明确重复的逻辑、协议和纯函数。
- 新增的抽象结构必须有实际的调用方（消费者），不允许凭空创造未被使用的功能。
- 保证向下兼容。新增能力的失败必须能够平滑回退到旧的执行链路。
- 严禁随意修改底层的 `workflow engine`（工作流引擎）、`executor`（执行器）和 `sandbox`（沙箱隔离）的核心语义。如果改动涉及命令执行、安全判断或调度逻辑，必须经过单独的评估与测试。
