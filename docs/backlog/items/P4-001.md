# P4-001: Secondary 能力是否恢复主线评估

> Status: done
> Priority: P4
> Source: Secondary capability assessment
> Module: `docs/design/secondary-capability-follow-up.md`
> Completed: 2026-06-08

## Description

Track the follow-up decision for whether secondary capabilities should remain secondary, be removed from visible product surfaces, or be restored to the main VectaHub product path.

The current assessment keeps `chat` in the main path and marks `serve`, `daemon`, `api`, `monitor`, `debug`, `generate`, `schedule`, `templates`, and `provider` for revisit after the main NL Workflow Orchestrator path is more stable.

## Expected

- Re-evaluate secondary capabilities against the main product chain.
- Confirm whether external integrations depend on each capability.
- Decide whether each capability should be kept, hidden, documented as secondary, merged into the NL path, promoted to primary, or removed from product-facing surfaces.
- Record evidence and rationale for each decision.

## Scope

- In-scope: serve, daemon, API, monitor, debug, generate, schedule, templates, and provider capability assessment
- In-scope: preserving `chat` as the current keep baseline unless new evidence contradicts it
- In-scope: product documentation alignment
- In-scope: follow-up contract gaps identified by the assessment
- Out-of-scope: deleting secondary capability code
- Out-of-scope: implementing new runtime integrations
- Out-of-scope: changing CLI command registration

## Verification Plan

1. Documentation links resolve with `npm run check:docs`.
2. Decisions are based on code, tests, documentation, or external integration evidence.
3. Any promoted capability has documented contract, verification, trace, and safety expectations.
4. Any capability kept as secondary has explicit product-surface guidance and follow-up contract work.

## Current Assessment Baseline

- `keep`: `chat`
- `revisit`: `serve`, `daemon`, `api`, `monitor`, `debug`, `generate`, `schedule`, `templates`, `provider`
- `remove`: none

## Planned Follow-up

1. Phase 1: document secondary positioning in product docs.
2. Phase 2: fill contract gaps for retained secondary capabilities.
3. Phase 3: integrate overlapping NL-related paths where justified.
4. Phase 4: revisit promotion decisions after main-path stability evidence exists.

## Open Questions

1. Which secondary capabilities have real external consumers today.
2. Whether any secondary capability should be hidden from default help output before removal is considered.
3. Whether `generate` and `templates` should remain separate user paths once NL planning is hardened.
