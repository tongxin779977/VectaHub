# P0-005: 建立 Command Surface Validator

> Status: done
> Priority: P0
> Source: Architecture alignment
> Module: `docs/contracts/cli-command-surface.md`, `src/commands/run.ts`
> Completed: 2026-06-08

## Description

Machine-readable CLI paths must not invent ad hoc JSON error shapes that drift from the documented command surface contract.

The current codebase already has a machine response envelope for orchestrator-style outputs, but `run.ts` still emitted a custom `{ ok: false, error: { ... } }` payload in several `--json` validation branches. That makes command-surface behavior inconsistent and weakens consumer expectations.

## Expected

- `run --json` validation and contract-boundary failures use a standardized machine response structure.
- Command-surface error payloads remain parseable as single JSON objects.
- The validator contract is enforced at the command boundary, not left to downstream consumers.

## Scope

- In-scope: `run.ts` JSON validation error path
- In-scope: command-surface contract alignment for machine-readable failures
- Out-of-scope: full command registry validation for every subcommand
- Out-of-scope: redesigning non-JSON human-readable errors

## Verification Plan

1. `run --json` validation failures produce the standardized machine response envelope.
2. Existing JSON output remains a single valid JSON object.
3. Typecheck and targeted tests pass.

## Completion

### Changes

- `src/commands/run.ts`:
  - switched JSON validation failure output from ad hoc `{ ok: false, error }` shape to `buildValidationErrorResponse(...)`
- `src/infrastructure/errors/index.test.ts`:
  - added assertions that the standardized error payload includes `schemaVersion`, `result.kind`, and `timestamp`

### Verification Evidence
