# VS Code 插件 UI 修复实施计划

## Problem

当前 VS Code 插件 UI 已存在统一设计依据，但实现层仍保留旧逻辑，主要问题包括：

- 文档任务中的 Agent 候选展示仍可能把内部配置态当成用户可见过滤条件。
- 内部状态同步与用户确认边界不清，容易把插件本应自动完成的动作转嫁给用户。
- 多处 UI 文案与流程仍更接近“实现快照”，尚未完全符合用户心智。

本计划用于把 [VS Code 插件 UI 逻辑设计](./vscode-ui-logic.md) 转成可执行修复清单。

## Goals

- 明确后续 UI 修复的实现范围、顺序和职责边界。
- 让开发者可以直接据此拆任务、写代码和补测试。
- 确保文档任务、权限提示、恢复入口和错误提示遵循同一套规则。

## Non-Goals

- 不在本计划中直接给出最终代码实现。
- 不要求本轮一次性重构所有插件 UI。
- 不扩展到 VS Code 插件以外的 CLI 或服务端 UI。

## Proposal

### 1. 修复范围

本轮 UI 修复聚焦以下范围：

- 文档任务中的 Agent 选择与自动收敛逻辑
- 文档任务执行前后的用户提示
- 风险确认与普通内部同步的边界
- 恢复入口的提示语义一致性
- 文档与实现的对齐

暂不包含：

- 全新的图形化 trace 视图
- 完整的恢复时间线 UI
- 非文档任务区域的大规模视觉重构

### 2. 修复原则

所有实现修复必须满足：

1. 用户只为真实决策负责  
   用户只需要决定是否执行风险操作、选择哪个可运行 Agent、是否重试失败任务。

2. 插件自动消化内部状态差异  
   配置态和运行态不一致时，优先由插件自动同步、自动修正或自动降级。

3. 运行事实优先于内部配置态展示  
   UI 是否展示候选，优先由“已安装、可调用、ready”决定。

4. 阻断必须解释真实原因  
   若无法执行，应说明“未安装”“入口不可调用”“真实外部授权缺失”等真实前置条件，而不是暴露内部字段。

### 3. 模块级修复清单

#### 3.1 `packages/vectahub-vscode-extension/src/commands/runDocTasks.ts`

职责：

- 获取 `tools agents --json`
- 构造 Agent 候选
- 选择执行 Agent
- 文档任务执行前后更新 UI 状态

需要修复：

- 不再仅用 `configured_enabled` 和 `has_permission` 决定候选是否可见。
- 将“候选展示规则”和“最终执行阻断规则”拆开。
- 为已确认可运行的 Agent 增加内部自动收敛路径。
- 调整告警和提示文案，避免直接暴露内部配置字段。

#### 3.2 `packages/vectahub-vscode-extension/src/views/tasksView.ts`

职责：

- 展示文档任务区域
- 显示任务状态和当前选定 Agent

需要修复：

- 确保展示文案体现“用户任务语义”，而不是内部状态语义。
- 若存在当前 Agent 摘要展示，应避免把内部状态问题描述成用户缺少操作。

#### 3.3 `packages/vectahub-vscode-extension/src/commands/docTaskRunHelpers.ts`

职责：

- 承接文档任务状态更新和运行记录辅助逻辑

需要修复：

- 保证内部状态回填、失败回滚和摘要更新不触发多余用户提示。
- 保证 UI 侧状态名称与统一设计保持一致。

#### 3.4 `src/commands/tools.ts`

职责：

- 提供 `tools agents --json`

需要修复：

- 保持 JSON 字段兼容，但明确区分运行事实与内部配置态。
- 如有必要，补充更利于 UI 使用的状态说明字段，但不能破坏现有消费方。

#### 3.5 `src/setup/cli-scanner.ts`

职责：

- 扫描 CLI 工具
- 更新内部配置态

需要修复：

- 明确哪些状态可以自动写回配置。
- 避免把一次扫描后的内部状态不同步长期遗留为 UI 问题。
- 若已有结构化运行事实，应优先推动配置态收敛。

### 4. 实施顺序

建议按以下顺序实施：

1. 先修正插件侧 Agent 候选展示逻辑  
   目标是先消除“明明可运行却被隐藏”的问题。

2. 再补内部自动收敛逻辑  
   让插件在读到结构化扫描结果后，不再长期卡在旧配置态。

3. 再统一提示文案与确认边界  
   把不必要的“启用/授权”交互收回到插件内部。

4. 最后补回归测试和文档引用检查  
   确保不会被后续改动带回旧行为。

### 5. 测试计划

#### 插件侧测试

建议新增或更新以下测试：

- 文档任务 Agent 选择测试  
  已安装、可调用、ready，但 `configured_enabled=false` / `has_permission=false` 的 Agent 仍会出现在候选中。

- 内部自动收敛测试  
  插件消费结构化扫描结果后，会自动修正可同步的内部状态。

- 提示文案测试  
  主提示不暴露 `configured_enabled`、`has_permission` 等内部字段。

- 风险确认边界测试  
  内部状态同步不会触发确认弹窗，高风险命令仍会触发确认弹窗。

#### CLI 侧测试

建议新增或更新以下测试：

- `tools agents --json` 字段兼容测试
- `cli-scanner` 自动同步测试
- 配置态与运行态不一致时的输出语义测试

### 6. 验收标准

修复完成后，必须满足：

- 已安装且可运行的 Agent，不会仅因内部配置态未同步而从 UI 中消失。
- 用户不需要为了继续文档任务，先执行与主任务无关的启用或授权按钮。
- 只有真实安全风险或真实外部前置条件缺失时，UI 才会打断用户。
- 主 UI 提示对普通用户可理解，技术细节进入输出面板或诊断入口。
- 插件、CLI 和文档对 Agent 可用性的定义不再互相冲突。

### 7. 风险与回滚

主要风险：

- 仅修改 UI 过滤而不处理内部自动收敛，会导致显示与执行仍不一致。
- 仅修改提示文案而不修改筛选逻辑，会继续保留核心问题。
- 过度在插件侧复制 CLI 判断，会破坏插件/CLI 边界。

回滚原则：

- 若修复导致执行链路出现真实回归，应优先保留结构化执行正确性，再回退局部 UI 表现层变更。
- 不允许为了恢复旧行为而重新把内部配置态直接暴露给用户。

## Tradeoffs

### 优点

- 将“设计文档”转成“可开发、可测试、可验收”的实施清单。
- 避免后续修复只停留在改一处过滤条件的补丁层面。

### 代价

- 需要跨插件和 CLI 两侧补充测试。
- 可能需要保留一段过渡期，在兼容旧 JSON 字段的同时更新 UI 行为。

## Test Plan

本计划本身不执行测试。后续每个实现任务完成后，至少应运行：

- 相关插件测试
- 相关 CLI 测试
- `npm run typecheck`

如某一侧缺少可直接执行的测试命令，应在实现任务中补充说明。
