# Agent Execution System Design

> Document Status: Target Design
> Authority: Owns the target Agent runtime architecture. Command semantics and runtime state are owned by the linked specs.
> Traceability: See `../contracts/implementation-traceability.md` for implementation status and known gaps.

## Problem

VectaHub should treat Agent CLI support as a runtime system capability rather than a hard-coded source patch.

The current project direction requires:

- a single dynamic Agent registry
- proactive onboarding when a user references an unknown Agent CLI
- a unified execution contract across CLI and VS Code
- mediated support for Agent CLIs that cannot natively run headless
- an LLM context model that teaches the LLM the registered Agent CLIs and VectaHub's own command capabilities

The core problem is not only "support more Agent CLIs". The deeper problem is that Agent runtime identity, invocation, readiness, approval handling, and execution mode must be modeled as first-class runtime data.

The LLM must not infer Agent CLI protocols from memory, raw `--help` output, or ad hoc prompt wording. It should receive a compact, structured context pack generated by VectaHub from runtime facts.

## Goals

- Use one runtime registry as the single source of truth for Agent CLI definitions.
- Let `run-task`, chat flows, and VS Code resolve Agent CLIs from the same registry.
- Support proactive discovery and onboarding when users reference an unknown Agent CLI.
- Distinguish native headless Agents from mediated interactive Agents and manual-only Agents.
- Keep VectaHub responsible for state, trace, safety, verification, and recovery even when the downstream Agent CLI is interactive.
- Make LLM calls aware of registered Agent CLIs, VectaHub command capabilities, execution modes, safety boundaries, and fallback limits.
- Keep command invocation rendering owned by VectaHub, while the LLM handles intent understanding, task semantics, and capability selection.

## Non-Goals

- Do not require every Agent CLI to natively support JSON output.
- Do not require every Agent CLI to natively support non-interactive execution.
- Do not generate TypeScript adapter source files at runtime.
- Do not let Agent output decide final task state.
- Do not introduce a second runtime registry or a parallel static source of truth.
- Do not let the LLM override registry-defined invocation transport, execution mode, preflight, approval policy, or runtime bootstrap rules.
- Do not feed full documentation, full CLI help, full stdout/stderr, secrets, or full trace data into routine LLM context.

## Proposal

### 1. Unified Dynamic Registry

Runtime Agent definitions should live in a single registry under `VECTAHUB_HOME`.

The registry should be the only runtime truth source for:

- Agent identity
- invocation shape
- prompt transport
- cwd transport
- preflight rules
- runtime bootstrap policy
- execution mode
- approval mediation rules
- capability hints
- LLM-facing summary fields
- validation status

Static seeded entries are acceptable only as a migration/bootstrap step. After seeding, the running system must read the registry only.

### 2. Execution Modes

Agent CLIs should be classified into three execution modes:

- `native_headless`
  - The Agent CLI supports stable non-interactive execution and can be launched directly.
- `mediated_interactive`
  - The Agent CLI does not provide a sufficient native headless interface, but VectaHub can execute it through a PTY-based interactive broker.
- `manual_only`
  - The Agent CLI can be discovered and registered, but cannot currently be executed safely through VectaHub automation.

This classification is a runtime capability decision, not a documentation label.

### 3. Agent Runtime Catalog

The Agent registry should expose an LLM-safe `Agent Runtime Catalog`.

This catalog is not a second registry. It is a derived view of the registry, designed for model context and UI selection.

Each catalog entry should include:

- `id`
- `displayName`
- `status`
- `executionMode`
- `installed`
- `invocable`
- `ready`
- `promptTransport`
- `cwdTransport`
- `structuredOutputSupport`
- `capabilities`
- `constraints`
- `source`
- `issues`
- `confidence`

The LLM-facing catalog must be compact and redacted. It must not include secrets, raw auth state, full config files, full help output, or complete runtime logs.

### 4. VectaHub Capability Catalog

VectaHub should expose its own command capabilities as structured data for LLM planning.

The catalog should describe VectaHub commands and internal capabilities such as:

- `run-task`
- `parse-doc`
- `tools agents`
- `tools agents onboard`
- `tools agents reprobe`
- `workflow run`
- `run-command`
- `security test`
- `recover-task`
- `trace show`

Each capability entry should define:

- purpose
- required inputs
- optional inputs
- side-effect level
- `--json` support
- `--dry-run` or preview support
- confirmation requirements
- output contract
- when the LLM should choose it
- when the LLM must avoid it

This lets the LLM choose VectaHub capabilities without guessing CLI syntax.

### 5. LLM Context Pack

Before any LLM call that needs project orchestration knowledge, VectaHub should build an `LLM Context Pack`.

The context pack should contain only the facts needed for the current decision:

- relevant registered Agent CLI summaries
- relevant VectaHub capability summaries
- current workspace execution constraints
- selected task contract summary when available
- safety and confirmation policy summary
- fallback and onboarding rules

The context pack must be generated from authoritative runtime sources. It must not be hand-maintained inside prompt text.

The LLM may use the context pack to:

- classify user intent
- select a VectaHub capability
- select a registered Agent CLI
- explain why an Agent is blocked, manual-only, or mediated
- draft task semantics from `AgentTaskContract`
- assist onboarding questions when confidence is insufficient

The LLM must not use the context pack to:

- invent command-line flags for registered Agents
- bypass `executionMode`
- bypass approval mediation
- mark an Agent ready without preflight
- infer success from Agent text output

### 6. Generic Invocation Renderer

VectaHub should replace hard-coded Agent-specific render classes with a generic invocation renderer driven by registry data.

The renderer should construct:

- command
- argv
- prompt transport
- cwd transport
- non-interactive flags
- runtime env patch
- mediated-interactive runner selection when required

The renderer standardizes how VectaHub invokes Agent CLIs. It does not assume that all Agent CLIs support the same execution capabilities.

For registered Agents, the renderer is authoritative. The LLM must not be asked to generate the registered Agent command shape.

### 7. Proactive Onboarding

When a user references an unknown Agent CLI in `run-task`, chat, or explicit Agent selection, VectaHub should:

1. detect whether the binary exists
2. probe version and help entry points
3. infer invocation shape
4. infer execution capabilities
5. validate a minimal preflight
6. persist a registry record
7. continue the original user flow when validation succeeds

If confidence is insufficient, VectaHub may ask the user a minimal number of targeted questions and then continue onboarding.

Onboarding output should update the registry and refresh the Agent Runtime Catalog. Chat, `run-task`, and VS Code should all observe the same result.

### 8. Mediated Interactive Execution

VectaHub should not drop support for Agent CLIs that lack native headless execution.

Instead, VectaHub should provide an interactive runner layer with:

- PTY-backed execution
- prompt classification
- approval brokerage
- timeout and hang detection
- trace integration
- output capture and redaction

This turns some interactive Agent CLIs into controllable `mediated_interactive` workers.

### 9. Approval Brokerage

Automatic approval must be policy-driven, not unconditional.

VectaHub should support:

- automatic allow for explicitly safe, validated, workspace-bounded prompts
- automatic deny for known unsafe prompts
- escalation to user confirmation for ambiguous, novel, or high-risk prompts

Approval mediation belongs to VectaHub system policy, not downstream Agent self-reporting.

### 10. External JSON Remains a VectaHub Contract

`run-task --json` should remain a VectaHub-owned structured protocol.

Downstream Agent CLIs do not need to emit JSON. VectaHub captures text output, redacts it, classifies execution results, and produces final structured JSON.

### 11. Plugin / CLI / LLM Consistency

The VS Code extension, CLI, and LLM prompt layer must not keep separate Agent capability models.

They should consume registry-derived results for:

- selectable Agent lists
- onboarding outcomes
- execution mode visibility
- readiness messaging
- blocked/manual-only feedback
- LLM-safe Agent summaries
- capability-aware routing

If the plugin, CLI, or LLM context disagree about whether an Agent is ready or executable, the registry-derived runtime state wins.

## Tradeoffs

| Choice | Decision | Why |
|------|------|------|
| Static built-in Agent table | Reject | It prevents dynamic discovery and keeps runtime truth fragmented. |
| Runtime-generated TypeScript adapters | Reject | It creates brittle code generation and a second implementation path. |
| Single dynamic registry + generic renderer | Adopt | It centralizes runtime truth and makes new Agent CLIs onboardable. |
| Fail closed for unsupported interactive behavior | Adopt | Safety and state correctness matter more than speculative automation. |
| PTY-mediated execution for some interactive CLIs | Adopt | It expands support without pretending all CLIs are natively headless. |
| LLM learns tools from raw help text | Reject | It is verbose, unstable, and lets protocol inference drift into prompt behavior. |
| LLM context pack from runtime catalogs | Adopt | It gives the LLM current capabilities without making it the protocol authority. |
