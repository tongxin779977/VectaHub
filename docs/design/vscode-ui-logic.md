# VS Code 插件 UI 逻辑设计

## Problem

当前 VS Code 插件的 UI 文档分散在多个入口中，存在三个问题：

- 用户视角和内部状态没有分层，开发容易把配置态直接暴露给用户。
- 同一条交互规则分别散落在 UI 文档、工具规格和实现中，容易互相冲突。
- 现有文档偏“现状描述”，缺少“后续修复必须遵守什么”的统一设计依据。

文档任务里的 Agent 选择问题就是典型例子：用户关心的是“哪个 Agent 现在能帮我执行任务”，而不是 `configured_enabled` 或 `has_permission` 这类内部字段是否已经同步。

## Goals

- 为 VS Code 插件建立一份统一的 UI 逻辑设计依据。
- 用用户任务和用户心智组织 UI 规则，而不是用内部模块组织。
- 明确哪些状态可以暴露给用户，哪些状态必须由插件内部自动收敛。
- 为后续修复文档任务、恢复、权限提示和 Agent 选择逻辑提供一致约束。
- 保持插件与 CLI 的边界清晰，避免 UI 复制执行逻辑。

## Non-Goals

- 不在本设计中定义 CLI 执行合同、trace 存储格式或状态机持久化细节。
- 不要求本轮文档修改后立即完成所有 UI 实现修复。
- 不把尚未实现的能力描述为已经完成。

## Proposal

### 1. 设计总原则

插件 UI 必须遵守以下原则：

1. 以用户目标为中心  
   用户的目标是完成任务，而不是理解内部配置、扫描状态或合同推导细节。

2. 默认自动化内部收敛  
   插件能够自动判断、自动同步、自动修正的内部状态，不应转嫁给用户处理。

3. 只在必要时打断用户  
   只有安全风险、破坏性操作、不可逆后果或无法自动推断的选择，才应触发确认。

4. UI 展示任务语义，不展示实现细节  
   用户看到的是“可执行”“不可执行”“需要确认”“执行失败”，而不是内部布尔位。

5. 结构化结果优先  
   插件应依赖 CLI JSON 或共享合同包，不应通过解析人类日志决定 UI 行为。

### 2. 用户可见层与内部状态层

UI 设计必须区分两层：

#### 用户可见层

用户可以看到或直接感知的内容：

- 当前能执行哪些动作
- 当前任务状态
- 是否需要安全确认
- 执行是否成功
- 失败后下一步怎么处理

#### 内部状态层

插件内部维护但不应直接要求用户理解的内容：

- CLI 扫描缓存
- `configured_enabled`
- `has_permission`
- 运行前预检缓存
- trace 关联细节
- 合同摘要缓存
- 配置与运行态的短暂不一致

规则：  
内部状态可以影响插件的执行决策，但不应直接成为用户必须处理的额外步骤，除非该状态代表真实外部前置条件尚未满足。

### 3. Agent 选择逻辑

Agent 选择必须以“用户想执行任务”为中心，而不是以“内部配置是否整洁”为中心。

#### 3.1 用户心智

用户关心的是：

- 我机器上有哪些 Agent 可以用
- 当前哪个 Agent 可以执行这个任务
- 如果不能执行，原因是什么
- 我需要做什么最少动作才能继续

用户不关心的是：

- 某个内部布尔值是否尚未写回配置
- 插件是否已经把扫描结果同步到本地配置文件

#### 3.2 展示规则

UI 中可供选择的 Agent 候选，应优先由运行事实决定：

- 已安装
- 可调用
- 任务入口 ready

如果 Agent 满足以上运行事实，即使内部配置态尚未同步，插件也不应直接把它从候选列表中隐藏。

#### 3.3 自动同步原则

当插件已通过结构化扫描确认某个 Agent 可运行时：

- 插件应优先自动修正或收敛内部配置态。
- 如果内部配置允许自动同步，不应要求用户额外点击“启用”或“授权”。
- 只有当真实外部授权尚未完成时，才应提示用户处理外部前置条件。

#### 3.4 不应出现的交互

以下交互不符合本设计：

- 因内部配置布尔值未同步而把可运行 Agent 从列表中隐藏。
- 要求用户先执行一个与主任务无关的“启用/授权”按钮，才能选择已可运行的 Agent。
- 把内部配置态错误包装成用户的操作责任。

### 4. 文档任务流程

文档任务 UI 应以“从文档到执行”为主线：

1. 选择文档
2. 解析任务
3. 选择可执行 Agent
4. 执行单任务或批量任务
5. 查看摘要结果
6. 在失败时进入恢复或重试路径

在这个流程中：

- 选择 Agent 是执行前的准备动作，不应成为额外配置流程。
- 文档任务列表展示任务语义和状态，不展示底层执行细节。
- 如果插件能够自动选定最近一次可用 Agent，可减少重复选择。

### 5. 权限确认与风险提示

UI 中的确认弹窗只能用于真实需要用户承担决策责任的场景。

#### 必须确认的场景

- 高风险或破坏性命令
- 删除、覆盖、清空等不可逆动作
- 恢复流程中的直接重试，如果可能扩大已有变更
- 插件无法自动判断安全性的关键分叉

#### 不应确认的场景

- 内部状态同步
- 已知可安全完成的 Agent 可用性收敛
- 纯展示态刷新
- 插件可自动重试的一次性预检

### 6. 错误提示原则

错误提示必须满足：

- 说明用户当前无法完成什么
- 给出最短恢复路径
- 不把内部字段名直接暴露给普通用户

示例：

- 好的提示：`未检测到可执行的 Agent，请先安装或修复 CLI 入口。`
- 不好的提示：`configured_enabled=false，has_permission=false`

如果需要保留技术细节，应进入输出面板或诊断入口，而不是主提示文案。

### 7. 恢复与状态展示

任务状态展示应服务于用户决策，而不是服务于内部状态机完整复刻。

主 UI 展示的状态应保持有限且稳定，例如：

- 等待执行
- 执行前检查
- 执行中
- 已产生修改
- 成功
- 失败
- 需要确认
- 已取消

更细的失败分类、trace 细节、合同摘要应进入运行记录、输出面板或专门入口。

### 8. 插件与 CLI 边界

插件负责：

- 用户入口
- 视图与交互
- 简单本地状态
- 风险确认
- 结构化结果渲染

CLI 负责：

- 扫描与执行
- 结构化 JSON
- 任务执行结果
- trace 与恢复结果

共享合同负责：

- 纯函数合同推导
- 可复用的结构化规则

规则：  
插件不能因为补 UI 逻辑而复制一套长期独立的执行真相。

### 9. 与当前实现的关系

当前仓库中已有部分 UI 文档、状态机规格和工具状态规格，但存在以下不一致：

- 某些规格把内部配置态直接定义为 UI 可见性条件。
- 某些流程文档只描述操作步骤，没有定义自动行为边界。
- 某些文档更像实现快照，而不是长期设计依据。

从本设计开始：

- 本文档是 VS Code 插件 UI 逻辑的统一设计依据。
- 具体实施顺序、文件落点和验收标准见 [VS Code 插件 UI 修复实施计划](./vscode-ui-remediation-plan.md)。
- 具体工作流文档应引用本文，而不是重新定义通用交互原则。
- 若现有规格与本文冲突，应优先修正文档与实现，使其符合用户心智。

## Tradeoffs

### 优点

- 后续修复有统一标准，不会继续把内部状态泄漏给用户。
- 开发可以明确知道哪些事情应该自动完成。
- 评审可以按用户心智检查 UI，而不是只按现有代码行为验收。

### 代价

- 需要修正文档间已有冲突，短期内会出现“设计已更新、实现未同步”的阶段。
- 某些旧字段仍会保留在 CLI JSON 中，但其 UI 含义会被收窄。

## Test Plan

后续实现修复应至少验证：

- 已安装且可运行的 Agent 不会因内部配置态未同步而被 UI 隐藏。
- 内部状态同步不会要求用户额外点击启用或授权。
- 高风险操作仍会触发确认弹窗。
- 失败提示对普通用户可理解，同时技术细节可在输出面板定位。
- 文档任务、恢复入口和任务面板文案遵循同一套 UI 规则。
